# Manager Playbook

This is for the manager whose people ask, "What should I actually use AI for?" and who doesn't want to answer with a blanket ban or a pep talk.

The aim is to help a team learn one useful way of working at a time. It shouldn't turn into performance monitoring, a large change programme or an unapproved technology project.

## The Manager's Job

You don't need to become the team's expert on every AI tool. Your job is to make four things easier:

1. choosing a safe task worth trying;
2. making it clear what good looks like;
3. helping people improve an early attempt; and
4. deciding whether a useful method should become a shared asset.

## Start With One Team Problem

Ask the team:

> Which repetitive part of our work would be useful to make clearer, quicker or more consistent, without changing a customer decision or a system automatically?

Good early candidates:

- first drafts of follow up emails;
- preparing questions for a meeting;
- turning approved notes into actions;
- organising a handover summary; or
- reviewing a fictional example together.

Keep early tests away from large data exports, customer messages nobody reviews, pricing, contracts, personal data and CRM automation.

## Run the First Session

Use [First Team Session](../workshops/first-team-session.md). What you want from it isn't a polished prompt. It's one shared example of:

- the task;
- the safe input;
- the output shape;
- the check a person applies; and
- what the team learned.

Fill in the [Team Learning Log](../templates/team-learning-log.md) as you go.

## Support the First Few Tests

Ask volunteers to use one small method in their normal work, but only where the information and the tool are approved. Your job is to clear obstacles, not to inspect every attempt.

At the end of a test, ask:

1. Which part of the output was useful?
2. What did you have to correct?
3. What input made the difference?
4. Would another person understand how to use this?
5. Is it safe and useful enough to test again?

If the answer is "not really", that's a useful result. Write it down and move on.

## Help Someone Improve a Weak First Prompt

Use [Improve a First Prompt](improve-a-first-prompt.md). The fix is rarely cleverer wording. It's usually a clearer job, better input, a useful output shape and a human check that the prompt states.

## Decide What Becomes Shared

Don't turn every good private prompt into team policy. Use the [Shared Team Asset Check](../checks/shared-team-asset-check.md).

An asset is ready only when:

- more than one person has found it useful;
- the safe input is clear;
- the output is easy to check;
- the common mistakes are known;
- someone owns keeping it current; and
- it doesn't make decisions or take actions automatically.

If it isn't ready, keep it in the learning log rather than publishing it as a team standard.

## Review Every Month

Run a short review:

| Ask | Why it matters |
| --- | --- |
| What did people use more than once? | Repeat use is stronger evidence than enthusiasm |
| What saved effort or improved quality? | It stops the review becoming a list of favourite tools |
| What created mistakes or uncertainty? | Failure is part of adopting AI safely |
| What should stay individual? | Not every method needs to become standard |
| What is ready for a shared asset? | The team only spreads what has proved useful |

The manager decides what the team does next. AI doesn't make that call.
